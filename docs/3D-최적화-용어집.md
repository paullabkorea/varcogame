# 3D 에셋 최적화 용어집

`Cartoon Wizard Boy.glb` 를 41MB → 2MB 로 줄이면서 나온 용어들을 정리했습니다.
궁금한 게 생기면 맨 아래 **[질문 노트](#질문-노트)** 에 적어두면 여기에 이어서 채웁니다.

---

## 1. 파일 구조 — glTF / GLB

| 용어 | 뜻 |
|---|---|
| **glTF** | 3D 씬을 담는 표준 포맷. "3D계의 JPEG"를 목표로 만든 규격. JSON + 별도 데이터 파일로 나뉨 |
| **GLB** | glTF를 **한 덩어리 바이너리**로 합친 것. 텍스처까지 전부 내장돼서 파일 하나로 끝남 |

GLB 내부는 이렇게 생겼습니다:

```
[12바이트 헤더]  magic="glTF", version=2, 전체 길이
[JSON 청크]      씬 구조 — 노드, 메시, 재질, 스킨 정보 (우리 파일은 8KB)
[BIN 청크]       실제 숫자 덩어리 — 버텍스 좌표, 텍스처 이미지 (우리 파일은 41MB)
```

> 우리 파일이 41MB였던 건 **JSON이 아니라 BIN 청크** 때문입니다. 구조가 복잡한 게 아니라
> 안에 든 데이터(폴리곤 + 텍스처)가 무거웠던 것.

| 용어 | 뜻 |
|---|---|
| **buffer / bufferView** | BIN 청크를 잘라 쓰는 단위. "이 바이트 몇 번부터 몇 개까지" |
| **accessor** | bufferView를 "의미"로 해석하는 층. "이건 VEC3 float32가 29만 개 = 버텍스 좌표" |
| **extensionsUsed** | 이 파일이 쓰는 확장 기능 목록 |
| **extensionsRequired** | **없으면 파일을 못 여는** 필수 확장. 뷰어가 지원 안 하면 로딩 실패 |

우리 최적화본은 `extensionsRequired: ["KHR_mesh_quantization"]` 입니다.
three.js GLTFLoader는 이걸 내장 지원하므로 추가 파일 없이 열립니다.

## 2. 지오메트리 — 메시의 구성 요소

| 용어 | 뜻 |
|---|---|
| **버텍스 (vertex)** | 꼭짓점. 위치·법선·UV 등을 묶어 가진 점 하나 |
| **폴리곤 / 삼각형 (tri)** | 버텍스 3개로 만든 면. GPU는 결국 전부 삼각형으로 그림 |
| **인덱스 (index)** | "3번, 7번, 12번 버텍스로 삼각형 하나" 처럼 버텍스를 재사용하는 번호표 |
| **메시 (mesh)** | 삼각형 덩어리 하나 |
| **버텍스 어트리뷰트** | 버텍스가 들고 다니는 속성들 |

### 버텍스 어트리뷰트 종류

| 이름 | 뜻 |
|---|---|
| `POSITION` | 좌표 (x, y, z) |
| `NORMAL` | 법선 — 면이 향한 방향. 빛 계산에 씀 |
| `TEXCOORD_0` | UV 좌표 — 텍스처 이미지의 어느 픽셀을 붙일지 |
| `JOINTS_0` | 이 버텍스가 어느 **본 4개**에 영향받는지 (본 번호) |
| `WEIGHTS_0` | 그 본 4개가 각각 **얼마나** 영향 주는지 (합이 1.0) |

> `JOINTS_0` / `WEIGHTS_0` 가 있으면 **리깅된 메시**입니다. 이게 없으면 뻣뻣한 조각상.

## 3. 리깅 관련 — "리깅"과 "애니메이션"은 다른 것

여기서 헷갈리기 쉬운 부분입니다.

| 용어 | 뜻 |
|---|---|
| **아마추어 / 스켈레톤 (armature/skeleton)** | 뼈대 전체 |
| **본 / 조인트 (bone/joint)** | 뼈 하나. glTF에선 그냥 노드(Node)입니다 |
| **리깅 (rigging)** | 뼈대를 만들고 계층(부모-자식)을 잡는 작업 |
| **스키닝 (skinning)** | 메시의 각 버텍스를 뼈에 **연결**하는 작업 |
| **스킨 웨이트 (skin weight)** | 그 연결의 세기. 웨이트 페인트로 칠하는 그것 |
| **바인드 포즈 (bind pose)** | 스키닝을 할 때의 기준 자세. 보통 T포즈/A포즈 |
| **inverseBindMatrices (IBM)** | 각 본의 바인드 포즈 역행렬. "이 본이 기준 자세에서 얼마나 움직였나"를 계산하는 기준점 |
| **애니메이션 클립 (animation clip)** | 시간에 따라 본을 어떻게 돌릴지 적어둔 **동작 데이터** |

### ★ 이번 파일에서 실제로 일어난 일

```
skins: 1          ← 리깅 있음 ✅  (Armature, 본 27개)
JOINTS_0/WEIGHTS_0 ← 스키닝 있음 ✅ (웨이트 합 전부 1.0, 오류 0개)
animations: 0     ← 애니메이션 클립 없음 ❌
```

**리깅은 정상적으로 들어가 있었습니다.** 없던 건 애니메이션 클립이에요.
뷰어에서 열면 T포즈로 가만히 서 있으니까 "리깅이 안 됐다"고 보였던 것.

블렌더에서 애니메이션까지 넣으려면 glTF 익스포트 시:
- **Animation → Animations** 체크
- Action이 **Fake User(방패 아이콘)** 로 보호돼 있는지 확인 (NLA에 스트립이 없으면 통째로 빠집니다)

지금 게임은 클립이 없는 대신 `src/player.js` 가 본을 직접 회전시켜
idle / 달리기 / 시전 동작을 코드로 만들어 쓰고 있습니다.

## 4. ★ 양자화 (Quantization) — 물어보신 것

**정밀도를 낮춰서 용량을 줄이는 기법**입니다. 사진을 24비트에서 8비트 색으로 줄이는 것과 같은 발상인데, 여기선 색이 아니라 **좌표 숫자**에 적용합니다.

### 원리

원래 버텍스 좌표는 `float32` — 숫자 하나에 **4바이트**를 씁니다.
float32는 소수점 아래 약 7자리까지 표현하는데, 키 1m짜리 캐릭터에겐 **터무니없이 과한 정밀도**입니다.

그래서 이렇게 바꿉니다:

```
1. 모델의 경계상자(bounding box)를 구한다        → 높이 0 ~ 0.9977m
2. 그 범위를 정수 눈금으로 나눈다                 → int16, -32768 ~ +32767
3. 좌표를 "몇 번째 눈금"인지로 저장한다           → 4바이트 → 2바이트
4. 원래 범위로 되돌리는 스케일 값을 따로 적어둔다
```

GPU가 읽을 때 스케일을 곱해 원래 좌표로 복원합니다(**dequantization**).

### 오차가 얼마나 되나

최종 파일에서 실제로 측정한 값입니다:

```
POSITION raw int16:  -31179, -1616, 908, -31171, -1524, 964, ...
값들의 최대공약수:    1          → 16비트를 꽉 채워 씀
서로 다른 값:         13,743개
정수 범위:            -32767 ~ +32767  (65,534단계)
```

축별 비율이 `31179/32767 = 0.95154`, 실제 bbox 비율이 `0.94894/0.99727 = 0.95154` 로
정확히 일치합니다 — 세 축이 **같은 눈금을 공유**하도록(비율이 안 깨지게) 스케일을 하나만 씁니다.

> 눈금 하나 = `0.99727m ÷ 65534` = **0.0152mm**

화면에서 캐릭터가 100픽셀 크기라면 오차는 **0.0015픽셀** — 눈으로 볼 수 없습니다.

실제로 이번 파일에서 원본과 최적화본의 스킨 결과를 비교하니:

```
ORIGINAL   size (0.94847, 0.99717, 0.46264)
OPTIMIZED  size (0.94894, 0.99727, 0.46277)
                  차이 0.0005 = 0.05%
```

### 양자화 = 정수화? 반올림?

**반올림이 본질에 더 가깝고, 정수화는 그 결과를 담는 형식**입니다. 한 줄 식으로 보면:

```
저장할 값 = round(원래값 ÷ 눈금크기)   ← 정수가 됨
복원한 값 = 저장한정수 × 눈금크기      ← 다시 실수로
```

| | 무엇에 해당하나 |
|---|---|
| **반올림** | 가운데 `round()` 라는 **행위** |
| **정수화** | 그 결과물의 **형태** |
| **양자화** | 이 식 **전체** — 특히 *눈금 크기를 정하고 그걸 따로 저장해두는 것* |

핵심은 세 번째입니다. `3.7 → 4` 같은 그냥 반올림은 눈금이 1로 고정이고, 되돌릴 정보가
없으면 그건 데이터 손실일 뿐입니다. 양자화는 **눈금 크기를 직접 정하고 그 값을 파일에
같이 넣어** 복원 가능하게 만듭니다.

> **정수 하나만으로는 의미가 없습니다. 정수 + 스케일이 한 세트**여야 양자화입니다.

### 정수가 아닌 양자화도 많다

"정수화"로 뭉뚱그리면 이런 것들을 놓칩니다:

| 방식 | 정수인가 | 설명 |
|---|---|---|
| **float16 / FP8** | ❌ | 여전히 부동소수점인데 양자화된 것. AI 모델 경량화의 주력 |
| **μ-law (음성)** | 정수지만 | 눈금 간격이 **일정하지 않음**. 작은 소리는 촘촘히, 큰 소리는 성기게 |
| **벡터 양자화 / 코드북** | 정수지만 | 값을 반올림하는 게 아니라 **대표값 목록의 번호**로 대체. 반올림이 아예 없음 |

마지막 것이 6장의 **KTX2 / Basis 텍스처 압축**입니다. 색을 반올림하는 게 아니라
"이 픽셀 블록은 팔레트 37번" 하고 번호를 적습니다.

### 어원

**양자(quantum) = 더 이상 쪼갤 수 없는 최소 단위.**
양자화는 *"최소 단위를 정하고 그 정수배로만 표현하겠다"* 는 뜻입니다.
**정수가 나오는 건 "최소 단위의 몇 배냐"로 세기 때문에 따라오는 결과**이지 정의가 아닙니다.

신호처리에서 짝을 이루는 개념과 비교하면 선명합니다:

| | 무엇을 자르나 |
|---|---|
| **샘플링 (표본화)** | **시간축**을 자름 — 1초에 44100번 |
| **양자화** | **값축**을 자름 — 진폭을 65536단계로 |

디지털 저울이 63.47kg을 63.5kg으로 표시하는 것 — 눈금 0.1의 양자화입니다.

> **한 줄 요약: 양자화 = 눈금 정하기 + 반올림 + 눈금 크기 기억해두기**

### 어트리뷰트별로 적용한 비트

| 어트리뷰트 | 원본 | 양자화 후 | 절감 |
|---|---|---|---|
| `POSITION` | float32 (4B) | int16 정규화 (2B) | 50% |
| `NORMAL` | float32 (4B) | int16 정규화 (2B) | 50% |
| `TEXCOORD_0` | float32 (4B) | uint16 정규화 (2B) | 50% |
| `WEIGHTS_0` | float32 (4B) | uint8 정규화 (1B) | 75% |
| `JOINTS_0` | uint8 (1B) | uint8 (1B) | — (이미 최소) |

### 정규화(normalized)란

정수를 **0~1 또는 -1~1 범위의 실수로 자동 변환**해서 읽으라는 표시입니다.

```
uint8  200  →  200 / 255  = 0.784   (0 ~ 1)
int16  -16384 → -16384/32767 = -0.5  (-1 ~ 1)
```

웨이트처럼 원래 0~1인 값은 이 방식이 딱 맞습니다. GPU가 하드웨어로 변환해줘서 공짜예요.

### 리깅과 양자화가 만나는 지점 (중요)

좌표를 정수로 바꾸면 스케일 보정이 필요한데, glTF 규격상 **스킨드 메시는 자기 노드의
transform을 무시**합니다(본 행렬로만 움직이니까). 그래서 노드에 스케일을 넣으면 안 됩니다.

gltf-transform은 대신 **inverseBindMatrices에 보정을 녹여넣습니다.** 실제로 값이 바뀌었어요:

```
원본     IBM[0] 이동성분: (-0.00037, -0.49797, +0.00051)
최적화본 IBM[0] 이동성분: (-0.00054, +0.00111, +0.00053)   ← 보정이 흡수됨
```

이게 제대로 안 되면 캐릭터가 터지거나 원점에 찌그러집니다. 그래서 위에서 스킨 결과 좌표를
직접 계산해 원본과 대조한 겁니다.

## 5. 폴리곤 줄이기

| 용어 | 뜻 |
|---|---|
| **데시메이션 (decimation) / 심플리파이 (simplify)** | 폴리곤 개수를 줄이는 것. 형태를 최대한 지키면서 삼각형을 합침 |
| **weld (용접)** | 같은 위치에 겹쳐 있는 버텍스를 하나로 합침. **심플리파이 전에 꼭 해야 함** — 안 하면 갈라진 틈에서 알고리즘이 멈춤 |
| **ratio** | 목표 비율. `0.08` = 버텍스를 8%만 남김 |
| **error** | 허용 오차 (모델 반지름 대비 비율). 이 한계에 먼저 걸리면 ratio에 못 가고 멈춤 |
| **reorder (버텍스 캐시 최적화)** | 삼각형 순서를 GPU 캐시에 잘 맞게 재배열. **용량은 그대로인데 렌더링이 빨라짐** |
| **prune** | 아무도 안 쓰는 데이터 삭제 |
| **dedup** | 완전히 같은 데이터가 중복 저장된 것을 하나로 합침 |

### 적정 폴리곤 수 감각

| 용도 | 삼각형 수 |
|---|---|
| 모바일 캐릭터 | 5,000 ~ 15,000 |
| **웹/캐주얼 게임 주인공** | **20,000 ~ 50,000** |
| PC 게임 주인공 | 50,000 ~ 150,000 |
| 영화/시네마틱 | 수백만 ~ |

원본 **500,000** 은 웹 게임 주인공으로는 10배 이상 과했습니다. → **40,000** 으로 조정.

> 참고: 딱 500,000이라는 반올림된 숫자는 **AI 3D 생성기나 포토그래메트리(사진 스캔)의
> 자동 감면 결과**일 때 나오는 전형적인 패턴입니다. 사람이 모델링하면 이런 숫자가 안 나와요.

## 6. 텍스처

| 용어 | 뜻 |
|---|---|
| **베이스컬러 (baseColor / albedo)** | 순수한 색 이미지. 그림자·하이라이트가 없는 "물체 본연의 색" |
| **노멀맵 (normal map)** | 표면 요철을 RGB로 인코딩한 이미지. 폴리곤을 늘리지 않고 굴곡을 흉내냄 |
| **UV** | 3D 표면을 2D 이미지에 펼친 좌표 |
| **밉맵 (mipmap)** | 텍스처를 절반씩 줄인 축소본 세트. 멀리 있는 물체에 작은 걸 써서 깜빡임(aliasing)을 막음 |

### 포맷

| 포맷 | 압축 | 특징 |
|---|---|---|
| **PNG** | 무손실 | 용량이 큼. **3D 에셋에 쓰면 안 되는 주범** |
| **JPEG** | 손실 | 작지만 투명도 없음, 노멀맵에 부적합 |
| **WebP** | 둘 다 가능 | 같은 화질에 JPEG보다 25~35% 작음. glTF에선 `EXT_texture_webp` 확장 |
| **KTX2 / Basis** | GPU 압축 | 최강. **압축된 채로 GPU 메모리에 올라감**(VRAM도 절약). 단 트랜스코더 파일 필요 |

이번엔 트랜스코더를 vendor에 추가하지 않으려고 **WebP**를 골랐습니다.
three.js GLTFLoader가 `EXT_texture_webp` 를 내장 지원해서 추가 파일이 0개예요.

### 해상도 감각

| 용도 | 해상도 |
|---|---|
| 화면에 크게 잡히는 주인공 | 2048 (2K) |
| 일반 캐릭터 / 소품 | 1024 (1K) |
| 배경 소품 | 512 |

원본은 **4096(4K) PNG** 였습니다. 탑다운 시점에서 캐릭터가 화면의 5%도 안 차지하는데
4K를 쓴 셈이라, 2K로 낮춰도 차이가 안 보입니다.

> **노멀맵 참고:** 이 모델의 노멀맵은 통계를 재보니 표준편차가 5 수준(평균 127.5)으로
> 거의 평평했습니다. 가장자리/이음새에만 정보가 있어서 1K로 줄여도 손실이 없었습니다.

## 7. 메시 압축 (이번엔 안 씀)

| 용어 | 뜻 | 왜 안 썼나 |
|---|---|---|
| **Draco** | 구글의 메시 압축. 압축률 최고 | 디코더 파일(~200KB) 별도 필요, 디코딩이 느림 |
| **meshopt (EXT_meshopt_compression)** | Draco보다 압축률은 조금 낮지만 **디코딩이 훨씬 빠름** | 디코더 파일(~50KB) 별도 필요 |

둘 다 `vendor/` 에 디코더를 추가해야 하는데, 양자화만으로 이미 2MB까지 내려와서
오프라인 실행 구조를 건드릴 이유가 없었습니다.

> 나중에 모델이 더 늘어나면 **meshopt** 를 추천합니다. Draco는 로딩 시 CPU를 오래 물어서
> 게임 시작이 오히려 느려질 수 있어요.

## 8. 이번 작업 요약

### 적용한 파이프라인

```
weld          겹친 버텍스 용접
  ↓

  ↓
dedup/prune   중복·미사용 데이터 제거
  ↓
reorder       GPU 버텍스 캐시 최적화
  ↓
텍스처 재인코딩  4K PNG → 2K WebP(q88) / 2K PNG → 1K WebP(q92)
  ↓
quantize      float32 → int16/uint8 정규화
```
