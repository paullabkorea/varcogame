# 룬가드 (RUNEGUARD)

> 무너진 제단, 마지막 수호자 — 룬의 불이 꺼지기 전까지 버텨라.

`Cartoon Wizard Boy.glb` 를 주인공으로 쓰는 Three.js 3D 마법 액션 게임입니다.
룬 제단 하나를 등지고 사방에서 몰려오는 적을 마법으로 밀어내는 **웨이브 생존 + 성장 룬 픽**
구조로, 라이브러리 없이 브라우저에서 바로 돌아갑니다.

## 실행 방법

**`start-game.bat` 을 더블클릭** 하면 로컬 서버가 뜨고 브라우저가 열립니다.
(`index.html` 을 그대로 더블클릭하면 브라우저 보안정책(CORS) 때문에 GLB 모델을 못 불러옵니다.)

수동으로 실행하려면:

```bash
python -m http.server 8765
# 브라우저에서 http://localhost:8765/index.html
```

인터넷 연결 없이도 동작합니다 (three.js 를 `vendor/` 에 포함).

## 적과 웨이브

일반 적 4종은 **GLB 모델**(`assets/models/`) 을 쓰고, 보스는 프리미티브를 조립해 만듭니다.

| 웨이브 | 등장 적 | 모델 | 특징 |
|---|---|---|---|
| 1 | 늪 슬라임 | `Cute Green Slime` | 통통 튀며 다가오는 기본형 |
| 2 | 해골 전사 | `Hooded Skeleton Warrior_2` | 맨손. 빠르게 붙는 근접형 |
| 3 | 해골 검사 | + `Barbarian Skull Sword` | 리치가 길고 한 방이 아픔 |
| 4 | 해골 술사 | + `Crystal Skull Staff` | 거리를 두고 지팡이 수정에서 마법탄 |
| 5+ | **혼성 무리** | — | 위 4종이 섞여서 몰려옴 |

`웨이브 % 5 == 0` 이면 **심연의 군주**(하수인 소환 + 광역 마법탄)가 얹힙니다.
즉 5웨이브가 첫 혼성 무리이자 첫 보스전입니다. 순서는 `src/enemies.js` 의 `INTRO` 배열이
정하고, 등장 수는 `COST` 표와 `5 + 웨이브×2.6` 예산으로 정해집니다.

웨이브마다 적의 수와 능력치가 올라가고, 경험치 구슬을 모아 레벨업하면
**성장 룬 3장 중 1장**을 골라 빌드를 굴립니다.

## 에셋 최적화

GLB는 전부 `assets/models/` 한 곳에 모아 뒀습니다. 게임이 읽는 건 최적화본 `*.opt.glb`
5개(합쳐서 **3.4MB**)이고, 원본은 `assets/models/source/` 에 재작업용으로 남겨 뒀습니다
(합쳐서 118MB — 지워도 게임은 돌아갑니다).

| 모델 | 원본 | 최적화본 | 감소 |
|---|---|---|---|
| Cartoon Wizard Boy (주인공) | 41.0 MB | **1.97 MB** | -95% |
| Cute Green Slime | 16.6 MB | **0.18 MB** | -98.9% |
| Hooded Skeleton Warrior_2 (리깅본) | 20.8 MB | **0.43 MB** | -97.9% |
| Barbarian Skull Sword | 19.1 MB | **0.38 MB** | -98.0% |
| Crystal Skull Staff | 19.6 MB | **0.40 MB** | -97.9% |

적 4종은 **주인공과 사정이 달랐습니다.** 삼각형이 이미 5,000개뿐이라 데시메이션할 게
없었고, 20MB가 전부 텍스처였습니다 (4096px PNG baseColor 15~16MB + 2048px PNG normal
2.6~4.3MB). 그래서 `simplify` 는 아예 끄고 텍스처만 다시 인코딩했습니다.

| 항목 | 원본 | 최적화본 |
|---|---|---|
| 삼각형 | 5,000 | **5,000 (그대로)** |
| baseColor | 4096px PNG | 1024px WebP q82 |
| normal | 2048px PNG | 512px WebP q92 (방향 벡터라 품질 높게) |
| 위치/노멀 | float32 | `KHR_mesh_quantization` |

파이프라인은 `weld → dedup/prune → reorder → 텍스처 재인코딩 → quantize` 입니다.
다시 굽거나 모델을 추가하려면 **[tools/optimize-glb.mjs](tools/optimize-glb.mjs)** 를 쓰세요.

확장은 `KHR_mesh_quantization` 과 `EXT_texture_webp` 두 개뿐인데, 둘 다 GLTFLoader가
**내장 지원**해서 `vendor/` 에 디코더를 추가할 필요가 없었습니다 (Draco·meshopt는 그래서 안 씀).

용어 설명은 **[docs/3D-최적화-용어집.md](docs/3D-최적화-용어집.md)** 에 정리해 뒀습니다.

## 적 모델을 쓰는 방식

적 GLB 에는 **애니메이션 클립이 하나도 없습니다.** 그래서 동작은 `src/enemies.js` 가
절차적으로 만드는데, 리그 유무에 따라 `src/models.js` 가 두 갈래로 처리합니다.

### 1) 해골 — 리그를 살려서 본으로 걷는다

`Hooded Skeleton Warrior_2.glb` 는 **23본 휴머노이드 리그**(Hips / Spine / Spine1 / Spine2 /
Neck / Head / 좌우 Shoulder·Arm·ForeArm·Hand / 좌우 UpLeg·Leg·Foot·ToeBase)가 들어 있습니다.
그래서 씬을 템플릿으로 두고 `SkeletonUtils.clone()` 으로 복제해 적마다 자기 스켈레톤을 줍니다.
지오메트리와 텍스처는 복제본끼리 공유됩니다.

본을 직접 굴릴 때 걸리는 문제가 둘 있었습니다:

1. **본마다 로컬 축(roll)이 제각각** — 그냥 `rotation.x` 를 만지면 본마다 다른 방향으로 꺾입니다.
   로드할 때 각 본의 rest 월드 회전을 이용해 "모델 공간 축"을 본 로컬 축으로 변환해 캐시해 두고,
   여러 축을 합성할 때는 누적 회전만큼 축을 보정합니다. (주인공 `Player._rotM()` 과 같은 방식)

2. **바인드가 T포즈** — 축 캐시는 rest 기준이라, T포즈를 기준으로 잡으면 팔을 내린 뒤의
   스윙 축이 어긋납니다. T포즈에서는 팔이 옆을 보므로 앞뒤 스윙이 **y축**인데,
   팔을 내리고 나면 **x축**이 되기 때문입니다. 그래서 로드 시점에 팔을 내려 A포즈를 만들고
   **그 자세를 rest 로 삼아 축 캐시를 다시 뜹니다** (`MODEL_DEFS.skeleton.restPose`).
   이후로는 걷기·공격을 전부 모델 공간 x/y/z 로 다룰 수 있습니다.

걷기는 허벅지·무릎·발을 좌우 반대 위상으로 굴리고, 팔은 같은 쪽 다리와 반대로 흔들고,
상체는 속도에 비례해 숙이면서 골반과 반대로 비틉니다. 공격은 오른팔을 머리 위로 젖혔다가
내려치고 몸통도 같이 돌아갑니다.

**무기는 `RightHand` 본에 그대로 매답니다.** 팔을 휘두르면 칼도 따라옵니다.
손 본은 모델 스케일을 물려받으므로 무기 스케일을 `1/handScale` 로 되돌리고,
손 본의 로컬 축이 제각각이라 원하는 "모델 공간 각도"를 본 로컬로 변환해서 넣습니다.

> 참고로 처음 받은 `Hooded Skeleton Warrior.glb` 는 **본이 없는 통짜 T포즈 메시**였습니다.
> 그때는 어깨를 축으로 정점을 직접 회전시켜 팔을 굽히고, 무기는 손 위치를 계산해 붙였습니다.
> `_2` 리깅본으로 바뀌면서 그 우회로는 전부 걷어냈습니다.

### 2) 슬라임·무기 — 바인드 포즈를 구워서 정적 메시로

슬라임(18본)은 스킨이 있지만 스쿼시&스트레치는 스케일로 충분하고, 칼·지팡이는
애초에 리그가 없습니다. 이런 모델은 로드할 때 **바인드 포즈를 지오메트리에 굽습니다** —
정점마다 블렌드 본 행렬 `bindMatrixInverse · (Σ wᵢ·boneMatᵢ) · bindMatrix` 를 만들어
위치와 노멀에 적용합니다. 런타임 스키닝 비용이 0이 되고 지오메트리를 통째로 공유합니다.

무기는 굽는 김에 원점도 옮깁니다. 칼은 모델이 날을 아래로 두고 서 있어서 뒤집고,
원점을 손잡이로 보내 손 본에 그냥 붙이면 되게 만듭니다. 지팡이는 수정 구슬 높이를
따로 기억해 **마법탄이 거기서 나갑니다** (`Enemy.muzzle()`).

### 씬 그래프

```
group          ← Enemy 가 위치·방향을 굴림
└ tilt         ← 몸 전체 기울기, 슬라임 스쿼시, 공격 시 몸통 회전
  └ body       ← 해골: 리그 살아있는 스킨 메시 / 슬라임: 구운 정적 메시
    └ …bones   ← RightHand 본에 무기가 매달림
```

재질은 적마다 복제합니다(피격 플래시가 따로 놀아야 해서). 텍스처가 있는 모델이라
평소 `emissive` 는 0으로 두고 맞을 때만 흰색으로 튀깁니다.
스킨 메시는 적마다 자기 `Skeleton`(= 본 텍스처)을 갖고 있어서 죽을 때 같이 버립니다.

## 주인공 애니메이션에 대해

이 GLB에는 **애니메이션 클립이 없고 스켈레톤(27본)만** 들어 있습니다.
그래서 `player.js` 에서 본을 직접 회전시켜 idle / 달리기 / 시전 동작을 만듭니다.

리깅(아마추어 + 스킨 웨이트) 자체는 정상적으로 익스포트돼 있습니다 — `animations` 배열만
비어 있는 것이라, 뷰어에서 열면 T포즈로 서 있어서 리깅이 빠진 것처럼 보입니다.
블렌더에서 클립까지 넣으려면 익스포트 시 **Animation → Animations** 를 켜고,
Action이 **Fake User(방패 아이콘)** 로 보호돼 있는지 확인하세요 (NLA 스트립이 없으면 통째로 빠집니다).

구현하면서 걸렸던 부분 두 가지:

1. **본 이름** — GLTFLoader 는 노드 이름을 sanitize 하면서 점을 지웁니다
   (`thigh.L` → `thighL`). `Player.bone()` 이 두 표기를 모두 해석합니다.
2. **회전 축** — 본마다 로컬 축(roll)이 제각각이라, 로드 시점에 각 본의
   rest 월드 회전을 이용해 "모델 공간 축"을 본 로컬 축으로 변환해 캐시해 둡니다.
   `_rotM()` 은 여러 축 회전을 합성할 때 누적 회전만큼 축을 보정해서,
   z로 팔을 내린 뒤 x로 스윙해도 비틀리지 않고 의도한 방향으로 움직입니다.

지팡이는 모델에 이미 포함돼 있어서(왼손 본에 스킨됨) 따로 만들지 않고,
스킨 웨이트를 훑어 **지팡이가 붙은 손과 그 끝(수정) 위치를 자동 탐지**해
마법 발사 지점으로 씁니다. 팔을 내리면 지팡이도 같이 눕기 때문에
손목에서 팔 회전을 역으로 상쇄해 지팡이가 늘 세워져 있게 했습니다.

## 손 모양 (손가락 본이 없는 리그)

리그가 `hand.L` / `hand.R` 에서 끝나고 **손가락 본이 없습니다**. 그래서 지팡이를 쥔
왼손은 모델링 단계에서 주먹이 잡혀 있지만, 빈 오른손은 T포즈의 쫙 편 손 그대로
굳어 있어서 손가락이 갈퀴처럼 벌어져 보였습니다. (원본 41MB 파일도 똑같습니다 —
최적화/데시메이션 때문에 뭉개진 게 아닙니다.)

본이 없으니 포즈로는 못 고쳐서, 로드 시점에 `Player._shapeHands()` 가
**바인드 포즈 지오메트리 자체를 한 번 구부립니다.**

1. 손 본 웨이트가 0.35 이상인 정점만 모아 손 본 로컬 공간으로 옮깁니다.
   (임계값을 낮추면 팔뚝·소매까지 딸려 들어와 손가락 축 계산이 팔 쪽으로 끌려갑니다.)
2. 손목에서 가장 멀리 뻗은 25% 정점의 평균 방향 = **손가락 축**,
   손끝 정점을 그 축에 수직인 평면에 투영해 공분산 주축을 구하면 = **손가락이 늘어선 축**.
3. 손가락 밑동부터 끝까지 각도가 비례해 커지는 벤드(bend) 디포머로 말고,
   동시에 벌어진 손가락을 가운데로 모읍니다. 노멀도 같은 각도만큼 돌려 줍니다.

스킨 웨이트는 건드리지 않으므로 이후 idle / 달리기 / 시전 포즈에 그대로 따라옵니다.
말리는 양은 `_curlFingers()` 안의 `CURL`(총 회전량) · `TUCK`(모으는 정도) ·
`VARY`(손가락별 편차) 세 상수로 조절합니다.

한 가지 주의: 최적화본은 위치·노멀이 `KHR_mesh_quantization` 으로 정수화돼 있어서
(`Int16Array` + `normalized`) 그대로 쓰면 값이 raw 정수로 나옵니다. 변형 전에
`Float32BufferAttribute` 로 풀어 두는 이유입니다.
